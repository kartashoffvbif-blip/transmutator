# transmutator

Локальный быстрый прокси-преобразователь входящих LLM-запросов на Go.

Сервис принимает HTTP-запросы клиентов, применяет к телу запроса
`POST /v1/chat/completions` цепочку jq-правил (для известных ключей),
отправляет результат на заранее заданный апстрим и возвращает ответ
апстрима клиенту без изменений. Стриминг (SSE) проксируется прозрачно.

Внешние LLM-вызовы, суммаризации, генерации, базы данных, горячая
перезагрузка правил и админка — отсутствуют по задумке.

## Как это работает

```
клиент ──▶ trasmutator ──▶ апстрим (upstream_url)
              │
              ├─ нецелевой запрос (не POST /v1/chat/completions)
              │    → прозрачный проброс: метод, путь, query, заголовки, тело
              │
              └─ целевой запрос (POST /v1/chat/completions)
                   1. тело не читается            → 500 (OpenAI-ошибка)
                   2. тело не валидный JSON       → проброс как есть
                   3. ключ неизвестен             → проброс как есть
                   4. правила не найдены          → проброс как есть
                   5. правила применяются последовательно (каждое с таймаутом)
                      ошибка/таймаут правила      → 500, запрос дальше не уходит
                   6. валидация результата
                      провал                      → 400, запрос дальше не уходит
                   7. успех                       → изменённое тело уходит на апстрим
```

Ключ берётся из заголовка `Authorization: Bearer <key>` (схема без учёта
регистра). Ключ используется только для выбора правил и пробрасывается
апстриму как есть.

Поле `model` для выбора правил берётся только из исходного тела запроса.
Если правила изменят `model`, повторный выбор правил не выполняется.

## Быстрый старт

```bash
# зависимости
go mod download

# сборка
go build -o transformer ./cmd/transformer

# подготовка конфигурации
cp config.example.yaml config.yaml   # отредактируйте upstream_url
cp rules.example.yaml rules.yaml     # отредактируйте ключи и фильтры

# запуск
./transformer -config config.yaml

# тесты
go test ./...
```

## Конфигурация

YAML-файл (см. `config.example.yaml`):

| Параметр      | Обязательный | Описание                                                      |
|---------------|--------------|---------------------------------------------------------------|
| `listen_addr` | да           | адрес прослушивания, например `":8080"`                       |
| `upstream_url`| да           | полный апстрим-URL для целевых запросов                       |
| `timeout`     | да           | таймаут выполнения одного правила, Go duration, больше нуля   |
| `debug`       | нет          | `false` по умолчанию; включает подробное логирование          |
| `log_file`    | нет          | файл для дубля логов (дозапись); пусто — только stdout        |
| `trace_dir`   | нет          | каталог файлов трассировки запросов; пусто — выключено        |
| `rules_file`  | да           | путь к манифесту правил                                       |

Если конфиг отсутствует или невалиден — сервис не стартует и печатает
понятную ошибку. Неизвестные ключи в YAML — ошибка конфигурации.

## Правила

Файл правил — YAML с верхнеуровневым ключом `rules` (см.
`rules.example.yaml`). Каждое правило:

| Поле            | Обязательное | Описание                                              |
|-----------------|--------------|-------------------------------------------------------|
| `key`           | да           | ключ клиента; точное совпадение, пустым быть не может |
| `model`         | нет          | модель; пусто/отсутствует = правило только по ключу   |
| `priority`      | нет          | целое, по умолчанию `0`; меньше — выполняется раньше  |
| `filter_file`   | одно из двух | путь к `.jq`-файлу (относительно файла правил)        |
| `filter_inline` | одно из двух | текст jq-фильтра, может быть многострочным            |
| `vars`          | нет          | переменные, доступные в фильтре как `$имя`            |

Указывать ровно один из `filter_file` / `filter_inline` обязательно.

**Групповая запись:** правило может вместо одного фильтра содержать
список `filters`; каждый его элемент — это приоритет, `vars` и ровно
один из `filter_file`/`filter_inline`. Группа разворачивается в
отдельные правила с общими `key` и `model`; внутри элементов `key`,
`model` и фильтр группы не задаются, `priority` и `vars` — только в
элементах. Выполняются по возрастанию `priority` как обычная цепочка.

```yaml
  - key: "sk-zcode"
    filters:
      - priority: 1
        filter_file: "my_rules/skills_list_rewriter.jq"
      - priority: 2
        filter_file: "my_rules/system_prompt_optimizer.jq"
```

**Выбор правил:** сначала ищутся правила с точным совпадением ключа и
модели (модель чувствительна к регистру). Если такие есть — применяются
только они. Иначе применяются правила, привязанные только к ключу.
Несколько подходящих правил выполняются по возрастанию `priority`;
при равном `priority` — в порядке следования в манифесте.

**Валидация при старте:** файл правил обязан существовать; каждое правило
проходят проверку структуры (непустой ключ, ровно один фильтр, файл
фильтра существует, имена переменных — валидные идентификаторы, значения
переменных — базовые типы) и компиляцию фильтра. Любая ошибка — сервис
не стартует. Пустой файл правил допустим: сервис работает чистым прокси.

**Семантика фильтра:** фильтр выполняется над всем телом запроса как
одним JSON-объектом и обязан вернуть ровно один результат. Ноль или
несколько результатов, ошибка или таймаут — ошибка правила (500), запрос
дальше не уходит. Результат должен быть объектом и пройти минимальную
валидацию (см. `validate_openai_request`), иначе — 400.

## Переменные

```yaml
vars:
  keep_last: 3
  word_to_remove: "SECRET"
```

```jq
.messages = (.messages | safe_truncate_blocks($keep_last))
| .secret_word = $word_to_remove
```

Поддерживаемые типы значений: строка, число, булево, массив, объект, null.

## Кастомные функции

Все функции детерминированы, локальны и без побочных эффектов.

### `approx_tokens` / `count_chars`

Приблизительный вес текста в символах (рунах). Это не токенизатор.

- строка → количество символов;
- массив → сумма весов элементов;
- объект → текст из полей `.text` и `.content` (content может быть
  строкой или массивом частей; текстовые части считаются, изображения
  и бинарные — нет);
- числа, булевы, null → 0.

```jq
"привет" | approx_tokens                          # 6
[{"type":"text","text":"мир"}] | approx_tokens    # 3
.messages | map(.content) | approx_tokens
```

### `safe_truncate_blocks(N)`

Безопасная обрезка истории сообщений по блокам вопрос-ответ. Вход —
массив сообщений, аргумент — сколько последних блоков оставить.

Блок начинается с сообщения с ролью `user` и включает все следующие за
ним `assistant`/`tool` до следующего `user`. Префикс до первого `user`
(обычно системные сообщения) сохраняется всегда. `N = 0` — только
префикс. Пары вопрос-ответ никогда не разрываются, сообщения не
изменяются, мультимодальный контент не трогается.

```jq
.messages = (.messages | safe_truncate_blocks(5))
.messages = (.messages | safe_truncate_blocks($keep_last))
```

### `validate_openai_request`

Минимальная валидация объекта запроса: возвращает вход без изменений
или падает с понятной ошибкой. Та же проверка автоматически выполняется
сервисом над результатом всех правил.

Проверяется: корень — объект; `messages` — непустой массив объектов со
строковой ролью; есть хотя бы один `user`; нет `assistant` до первого
`user`; каждое `tool`-сообщение имеет строковый `tool_call_id` и
ссылается на ранее объявленный вызов; все `tool_calls` закрыты
`tool`-ответами. Неизвестные поля игнорируются.

```jq
.messages |= map(select(.role != "system")) | validate_openai_request
```

## Примеры типовых правил

```jq
# обрезать историю до последних 5 блоков
.messages = (.messages | safe_truncate_blocks(5))

# заменить системный промпт, а если system-сообщений нет — дописать в начало
([.messages[] | select(.role == "system")] | length) as $n
| .messages =
    if $n > 0
    then [.messages[] | if .role == "system" then .content = "новый промпт" else . end]
    else [{"role":"system","content":"новый промпт"}] + .messages
    end

# очистить описания всех инструментов
.tools |= map(if has("description") then .description = "" else . end)

# удалить инструмент по имени
.tools |= map(select(.name != "expensive_tool"))

# заменить слово в текстовых сообщениях
.messages |= map(if (.content | type) == "string" then .content |= gsub("SECRET"; "REDACTED") else . end)

# префикс к системному сообщению
.messages |= map(if .role == "system" then .content = "важно: " + .content else . end)
```

## Формат ошибок

Все ошибки клиенту — валидный JSON в стиле OpenAI:
`{"error": {"message": "...", "type": "...", "code": "..."}}`.

| Ситуация                          | HTTP | type                   | code                          |
|-----------------------------------|------|------------------------|-------------------------------|
| тело запроса не прочитано         | 500  | invalid_request_error  | request_body_read_failed      |
| ошибка выполнения правила         | 500  | transformation_error   | rule_execution_failed         |
| таймаут правила                   | 500  | transformation_error   | rule_timeout                  |
| результат не прошёл валидацию     | 400  | invalid_request_error  | invalid_transformed_request   |
| апстрим недоступен                | 502  | upstream_error         | upstream_unreachable          |

Ошибки, которые вернул сам апстрим, передаются клиенту как есть.

## Логирование

Структурированные логи на стандартном `log/slog` (text handler).

- **Обычный режим** — только ошибки обработки запросов. Сообщения старта
  и остановки сервиса имеют уровень Info и видны только в debug-режиме.
- **Debug-режим** (`debug: true`) — плюс: выбранная цепочка правил,
  метрики до/после (размер в байтах и приблизительное количество
  символов) и ссылка на файлы трассировки. Сами тела в текстовый лог
  не пишутся — экранирование slog делает нечитаемыми многострочный
  JSON; они идут в файлы трассировки.

### Дубль логов в файл

`log_file: "transformer.log"` — логи пишутся одновременно в stdout и в
указанный файл (дозапись при перезапусках). Перенаправление `2>&1 | tee`
при этом не нужно.

### Трассировка запросов

`trace_dir: "logs"` (только при `debug: true`) — для каждого
преобразования в отдельные файлы с меткой времени и порядковым номером
пишутся читаемые артефакты без экранирования:

```
logs/20261015-171500.000042-request.json       исходное тело (pretty JSON)
logs/20261015-171500.000042-transformed.json   результат (pretty JSON)
logs/20261015-171500.000042-diff.patch         построчный diff (-/+)
```

Каталог создаётся при старте; `logs/` добавлен в `.gitignore`.

## Архитектура

```
cmd/transformer/       точка входа: конфиг, правила, сервер, graceful shutdown
internal/config        загрузка и валидация YAML-конфига
internal/rules         модель правила и селектор (ключ/модель/приоритет)
internal/storage       интерфейс Store + файловая реализация (YAML-манифест,
                       внешние .jq-файлы); позже можно заменить на SQLite
internal/transform     компиляция gojq-фильтров, нормализация значений,
                       последовательное выполнение с таймаутом
internal/jqfuncs       кастомные jq-функции
internal/validation    минимальная валидация результата
internal/proxy         проброс запросов и стриминг ответов без изменений
internal/httpapi       главный обработчик: маршрутизация, цепочка правил
internal/errs          типизированные ошибки в стиле OpenAI
internal/logging       настройка slog, tracer (файлы трассировки) + diff
internal/testhelpers   тестовый записывающий апстрим
```

Зависимости: стандартная библиотека, `github.com/itchyny/gojq`,
`gopkg.in/yaml.v3`.

## Допущения

Зафиксированные решения в местах, где спецификация допускала трактовки:

1. Целевой путь — строго `POST` с точным путём `/v1/chat/completions`
   (без учёта trailing slash); всё остальное — нецелевое.
2. Тело целевого запроса читается в память целиком (преобразованию нужен
   полный JSON); ограничение на размер тела не вводится.
3. Если корень валидного JSON — не объект (или `model` не строка), поле
   `model` считается отсутствующим: поиск идёт только по ключу.
4. Если у `upstream_url` уже есть query-параметры и они есть у исходного
   запроса, они объединяются через `&`.
5. Hop-by-hop заголовки (`Connection` и перечисленные в нём, `Keep-Alive`,
   `Te`, `Trailer`, `Transfer-Encoding`, `Upgrade`) не пересылаются;
   `Content-Length` пересчитывается по новому телу; остальные заголовки
   запроса пересылаются как есть, включая `Authorization`.
6. Ответ апстрима возвращается байт-в-байт: сжатие на стороне прокси
   отключено, статус/заголовки/тело не модифицируются.
7. Фильтр, вернувший не-объект, классифицируется как ошибка валидации
   (400, `invalid_transformed_request`); ноль или несколько результатов —
   как ошибка выполнения правила (500, `rule_execution_failed`).
8. Валидация результата выполняется один раз, после всех правил.
9. `tool_calls` у assistant-сообщения, если задан не как null, должен
   быть массивом объектов со строковым непустым `id`.
10. Роли `user`/`assistant`/`tool` сравниваются с учётом регистра.
11. Ключ из `Authorization` обрезается по пробелам; пустой токен считается
    неизвестным ключом.
12. `timeout` действует на одно правило; суммарное время цепочки из N
    правил может достигать N × timeout.
13. Правила с совпавшими ключом/моделью применяются все (не только первое).
14. Пустой (0 байт) файл правил считается файлом без правил — сервис
    стартует и работает чистым прокси.

## Известные ограничения

1. Горячая перезагрузка правил отсутствует: правила читаются один раз
   при старте; для обновления нужен перезапуск.
2. Хранилище правил только файловое (интерфейс `storage.Store` позволяет
   добавить SQLite позже).
3. Один апстрим для всех клиентов; маршрутизации по ключу/модели нет.
4. Тело целевого запроса буферизуется в памяти целиком.
5. Ответы апстрима не преобразуются и не логируются в обычном режиме.
6. Параллельное выполнение правил отсутствует — по спецификации.
7. Правила не имеют доступа к файловой системе, сети и переменным
   окружения; исполняемый код в правилах невозможен (только jq-фильтры).
